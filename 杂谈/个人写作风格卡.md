# 个人写作风格卡

## 使用目标

这张风格卡用于让`Codex`在我明确提出“按我的风格写”“像我写的”或“去AI化成我的口吻”时，参考我过去的真实笔记去生成或改写内容。

目标不是复制我的错别字和病句，也不是把所有文章改成同一种模板，而是在修正明显错误的同时保留我的选材方式、解释顺序、个人判断和实际开发经历。主要读者是我自己以及刚接触相关技术的初学者。

对应本地技能为：`$zhou-writing-style`

## 语料边界

- 正文以`---`开头并包含`YAML`属性块的笔记统一视为`AI`样本，不参与个人风格正样本提炼。
- 没有顶部属性块的笔记可以作为本人候选样本，但仍需排除密码、`Token`、`API Key`等敏感信息。
- 正样本只用来学习表达和组织方式，不能作为新技术事实的依据。
- `AI`样本只用来识别应避免的模板化结构，不能反向混入本人风格。
- 风格刷新必须由我明确提出，日常调用不能随机更换样本。

## 共享写作底色

### 从实际问题出发

写技术内容时优先说明为什么会接触这个问题、当前使用的设备或软件是什么、实际操作中遇到了什么限制。不要先写“随着技术的发展”等大而空的背景。

文章中真正有价值的信息通常包括：

- 为什么需要做这件事
- 实际执行了什么操作
- 哪一步出现了问题
- 问题发生后如何判断原因
- 最后通过什么现象确认操作生效

### 保留真实个人声音

- 有真实经历、动机和判断时可以直接使用“我”；带读者操作时可以使用“我们”。
- 可以保留真实的犹豫、失败、自我吐槽和前后观点变化，不需要把作者塑造成从不犯错的人。
- 不为了增加“人味”虚构经历、设备、故障、结果、情绪或观点。
- 缺少个人经历时宁可先列出事实缺口，也不能编造第一人称内容。

### 解释方式

- 面向初学者时，可以把新概念与已经熟悉的`C`、`C++`、`Java`、`Keil`、`Windows`或裸机开发进行比较。
- 使用类比时只保留真正能帮助理解的一种，并说明到足够理解即可，不堆砌比喻。
- 命令、路径、配置项、截图和验证结果应放在对应解释附近。
- 技术名词、文件名、命令和代码标识符可以使用反引号，方便后续快速查看。

### 句子和结构

- 允许长短句交替。因果关系较长时可以逐步说清楚，再用短句结束当前判断。
- 修正明显错字、错误代词、重复词、病句和损坏的`Markdown`，不刻意复刻错误。
- 标题围绕真实内容设置，例如“简介”“作用”“配置”“实操”“结果验证”，不强行把每篇文章凑成相同章节。
- `总结`不是必选项。没有新的判断、结果或下一步时可以直接结束。

## 四种体裁

### 概念卡片

识别条件：主要解释一个术语、机制、区别或编程概念，用于快速复习。

组织方式：

1. 直接给出定义。
2. 解释它关注什么或如何工作。
3. 必要时与熟悉的语言、工具或相邻概念比较。
4. 添加一个小例子、组成列表或相关笔记链接。
5. 内容够用后停止，不固定添加总结和参考资料。

### 实操教程

识别条件：读者需要按顺序完成安装、配置、移植、构建、烧录或验证。

组织方式：

1. 说明真实开发背景和为什么需要这项操作。
2. 只列会影响结果的前置条件。
3. 按实际操作顺序设置标题。
4. 在操作旁解释非直观配置的作用。
5. 把警告放在它约束的步骤附近。
6. 用真实验证结果结束，不能只写“配置完成”。

### 项目复盘／运行手册

识别条件：用于项目部署、重复运行、故障恢复、命令备忘或迁移总结。

组织方式：

1. 先说明电脑、开发板、进程或服务分别负责什么。
2. 按运行位置或操作阶段组织内容。
3. 保留准确的命令、路径、环境变量、健康检查和预期输出。
4. 记录修改后是否需要重启、重新编译或重新加载环境。
5. 当前方案与旧方案并存时明确标记，优先保证以后能快速查到。
6. 为了避免在错误环境执行命令，可以保留必要重复。

### 个人叙事

识别条件：重点是亲身经历、学习过程、失败、决策或观点变化，而不是让读者照着完成操作。

组织方式：

1. 交代真实时间、学习或项目背景，以及当时的想法。
2. 按真实尝试或转折推进。
3. 保留具体设备、软件、人物、限制、错误和后果。
4. 允许现在的自己评价过去的判断。
5. 在真实决定、未完成的问题或转入教程的位置结束。

个人叙事不虚构电影化场景、对话和情绪，也不把每次失败都升华成成长故事。

## 需要避免的AI写法

- 没有证据的意义拔高，例如“里程碑”“深远影响”“赋能”。
- 宣传工具魅力、强行鼓励读者或保证操作一定简单。
- 每篇文章都使用整齐的三段式、相同章节数量和固定“常见问题/参考资料”结尾。
- 无来源的“研究显示”“业内人士认为”和其他模糊归因。
- 正文中残留“当然可以”“希望对你有所帮助”等聊天机器人话术。
- 为了显得完整而添加没有信息量的总结。
- 过度润色成百科或新闻稿，导致真实动机、疑问和判断被删除。

通用`humanize-text`规则只能用来清理这些通用`AI`痕迹。如果通用规则与本风格卡中经过真实样本确认的习惯冲突，以本风格卡为准，但事实准确性和基本可读性始终优先。

## 生成和写回规则

1. 自动识别主要体裁，也可以由我手动指定。
2. 根据材料区分事实、个人观点、亲身经历和未知信息。
3. 缺少必要的个人事实时先询问，不能自行补写。
4. 先展示完整正文、事实缺口、风格自检和预计来源属性。
5. 我确认后才能通过`Obsidian MCP`创建或修改笔记。
6. 修改已有笔记前先读取目标并确认仓库相对路径。
7. `Obsidian MCP`不可用时只报告连接错误，不能改用本地文件系统写入。

新建或实质改写的`AI`笔记需要添加：


## 验收和更新

四种体裁分别使用一篇未参与提炼的本人笔记进行盲测。每篇从以下方面判断：

- 像不像我
- 好不好读
- 事实是否可靠
- 体裁是否正确
- 最不像我的一句或一处是什么

是否通过最终由我判断，不使用所谓`AI`检测分数代替人工判断。

当我说“刷新我的写作风格”时，重新筛选每类三篇锚点和一篇盲测样本，先让我确认名单，再升级风格卡和本地技能版本。新版本通过四种体裁测试前保留旧版本。
