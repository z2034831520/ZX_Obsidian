## 简介
在`FreeRTOS`中定时器分为硬件定时器和软件定时器，这两种定时器的应用场景和实现机制并不一样，在早期的`HAL`库裸机开发中我们只使用到了系统自带的系统滴答定时器作为系统的时钟源，当我们开始使用`FreeRTOS`时我们仍旧是使用系统的滴答定时器作为对应的时钟源。但是在裸机开发中我们称自己使用的是硬件定时器，而到了`FreeRTOS`中我们却又改口说自己使用的是软件定时器了。明明我们使用的定时器都是一样的，为什么换了一个场景叫法就不一样了呢？接下来我们就会深入的了解一下二者的差异，以及为什么会这么叫

## 裸机开发
在裸机开发中如果我们想要让一个小灯每隔`500ms`进行一次亮灭，对应的代码实现非常简单，我们只需要在两次引脚高低电平状态切换之前进行一次`500ms`的系统延时即可，对应的代码实现如下：
```c
while (1) 
{ 
	// 翻转 LED1 状态 
	HAL_GPIO_TogglePin(LED1_GPIO_Port, LED1_Pin); 
	// 延时500ms
	HAL_Delay(500); 
}
```

如果我们现在需要再控制一颗小灯每隔`200ms`进行一次亮灭呢？代码的复杂度一下子就上来了，代码的实现为：
```c
uint32_t last_led1_tick = HAL_GetTick(); 
uint32_t last_led2_tick = HAL_GetTick(); 
while (1) 
{ 
	// 每次循环都要获取当前系统时间 
	uint32_t current_tick = HAL_GetTick(); 
	/* --- 处理 LED1 任务 --- */ 
	if (current_tick - last_led1_tick >= 500) 
	{ 
		HAL_GPIO_TogglePin(LED1_GPIO_Port, LED1_Pin);  
		last_led1_tick = current_tick; 
		// 更新时间戳
	} 
	 /* --- 处理 LED2 任务 --- */ 
	if (current_tick - last_led2_tick >= 200) 
	{ 
		 HAL_GPIO_TogglePin(LED2_GPIO_Port, LED2_Pin); 
		 last_led2_tick = current_tick; // 更新时间戳 
	}
}
```
仅仅只是增加了一个小灯，我们就需要添加对应的时间戳变量和对应的`if`判断，这是极不经济的做法。如果我们还希望能够再控制传感器去实时读取环境数据呢？因此我们就需要通过使用硬件定时器来将任务分隔开来，我们只需要配置一下定时器的中断触发参数，然后就可以在定时器的中断回调函数中直接完成对应的外设操作。这是在裸机开发环境下多任务的管理方式
### 硬件定时器的本质
硬件定时器是我们在裸机开发中的全部，只要我们一打开`CubeMX`映入眼帘的就有`Timers`选项，点开之后我们就可以看到当前芯片上可供使用的硬件定时器
![](assets/硬件定时器%20VS%20软件定时器/file-20260726163931180.png)
我们涉及到所有与延时相关的动作都需要依靠他们来实现，硬件定时器的精度和实时性都很高，可以满足一些高精度场景下的需求，例如电机控制等

在裸机开发中系统的时间基准永远只有一个，当我们需要执行延时或者周期性任务的时候，我们编写的代码往往都是直接去读取或修改底层物理寄存器中保存的值。比如在`HAL`库中常用的`HAL_Delay()`函数，本质上就是开启了`SysTick`硬件中断，每次中断让一个全局变量`uwTick`加一，在这种交互模式下，我们是直接与硬件电路在打交道

## FreeRTOS开发
当我们引入了`FreeRTOS`后，`SysTcik`这个硬件定时器被操作系统“独占”了

- `FreeRTOS`会强制把`SysTick`变成整个系统的心跳
- 作为开发者，我们无法再去直接操控`SysTick`的底层寄存器器去进行读取和修改操作了
此时就会产生一个问题，如果我们需要10个不同的定时功能（比如：`LED`每5秒闪烁一次、`WIFI`每秒发送一次数据），但是此时`SysTick`已经被系统征用了，其它的硬件定时器（TIM1/TIM2）又不够用，此时应该怎么办？这就是`FreeRTOS`软件定时器产生的原因

### 软件定时器的本质
`FreeRTOS`中的软件定时器本质上就是一个普通的系统后台任务，当我们开启了对应的定时器功能时，`FreeRTOS`就会在后台创建一个名为`Tmr Svc`的专属任务，后续所有的任务回调函数都是依靠这个它来执行的，大致的运行流程为：
1. 系统会创建一个有序链表，在链表中激活的定时器会按到期时间升序排列，最先到期的永远排在第一个
2. 守护任务会去查阅链表中第一个也就是最先执行任务的剩余时间，比如还有50毫秒，它就会把这50ms设置未阻塞超时时间
