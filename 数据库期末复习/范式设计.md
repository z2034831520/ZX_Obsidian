## 简介
数据库的范式是关系型数据库设计中的一系列规则和指导原则，它的核心目标是减少数据冗余并减少数据操作异常，在日常开发中最常使用的是前三个范式（1NF、2NF、3NF），一般认为，满足第三范式的数据库设计就已经是一个结构良好的规范化数据库了

## 第一范式
### 内容介绍
核心原则：表中的每一列都是不可分割的最小数据单元，不能包含集合、数组或多个值

### 解决问题
如果某个字段里塞进了多个数据，导致无法对单一数据进行高效查询或统计

### 示例
**改造前（不符合 1NF）：**

| **学生 ID** | **姓名** | **选修课程**    |
| --------- | ------ | ----------- |
| 101       | 张三     | 计算机网络, 操作系统 |
| 102       | 李四     | 数据库原理       |
分析：选修课程字段包含了多个值，违反了原子性，如果想要查询“选修了操作系统的学生”，需要使用低效的模糊匹配

**改造后（符合 1NF）：**

| **学生 ID** | **姓名** | **选修课程** |
| --------- | ------ | -------- |
| 101       | 张三     | 计算机网络    |
| 101       | 张三     | 操作系统     |
| 102       | 李四     | 数据库原理    |

## 第二范式
### 内容介绍
在满足第一范式的基础上，表中所有非主属性必须完全依赖与整个主键，而不能只依赖于主键的一部分

### 解决问题
表中记录了两个实体的混合信息，导致数据大量重复，更新某一个信息时需要修改多行记录

### 示例
**改造前（符合 1NF，不符合 2NF）：**

假设复合主键是 `(学生 ID, 课程 ID)`。

|**学生 ID**|**课程 ID**|**成绩**|**学生姓名**|**课程学分**|
|---|---|---|---|---|
|101|C01|90|张三|4|
|101|C02|85|张三|3|
|102|C01|92|李四|4|
分析：成绩依赖于`(学生 ID, 课程 ID)`这个完整的主键，但是学生姓名只依赖于学生ID，课程学分只依赖于课程ID，这就是部分依赖，这会导致张三这个名字和C01这个课程有4个学分这个信息被冗余存储

**改造后（符合 2NF）：**

将原表拆分为三个表，各自负责独立的实体关系：

**1. 学生表**

|**学生 ID**|**学生姓名**|
|---|---|
|101|张三|
|102|李四|

**2. 课程表**

|**课程 ID**|**课程学分**|
|---|---|
|C01|4|
|C02|3|

**3. 成绩表**

|**学生 ID**|**课程 ID**|**成绩**|
|---|---|---|
|101|C01|90|
|101|C02|85|
|102|C01|92|

## 第三范式
### 内容介绍
在满足第二范式的基础上，任何非主属性必须直接依赖于主键，不能依赖于其他的非主属性

### 解决问题
表中的某个字段可以通过另外一个非主键字段推导出来

**改造前（符合 2NF，不符合 3NF）：**

主键为 `员工 ID`。

|**员工 ID**|**姓名**|**部门 ID**|**部门名称**|**部门位置**|
|---|---|---|---|---|
|1|王五|D1|研发部|科技园A栋|
|2|赵六|D1|研发部|科技园A栋|
|3|孙七|D2|市场部|商务中心B座|
在上述表中，主键是`员工ID`，部门名称和部门位置实际上是依赖于`部门ID`的，而`部门ID`依赖于`员工ID`，存在`员工 ID -> 部门 ID -> 部门名称/位置`的传递依赖，如果在研发部新加入100个员工，“研发部”和“科技园A栋”就会被重复存储100次。

**改造后（符合 3NF）：** 剥离传递依赖的部分，建立独立的表。
**1. 员工表**

|**员工 ID**|**姓名**|**部门 ID**|
|---|---|---|
|1|王五|D1|
|2|赵六|D1|
|3|孙七|D2|

**2. 部门表**

|**部门 ID**|**部门名称**|**部门位置**|
|---|---|---|
|D1|研发部|科技园A栋|
|D2|市场部|商务中心B座|
